Two files under `_meta/` describe the whole company: who exists (`org.yaml`) and who sees what (`spaces.yaml`) — plus an optional third, `webhook.yaml`, when you run the [webhook intake receiver](/guides/getting-things-in#webhooks--automatic-intake-from-other-services). All are plain YAML, validated on load — a malformed file is a clear error, never a silent misconfiguration. Nothing under `_meta/` is ever compiled into a person's vault. brainkit also *writes* one file there itself — the health snapshot every cycle refreshes for a control plane to read, documented at the end of this page.

## `org.yaml`

```yaml
people:
  admin: {name: Admin, roles: [admin]}   # dedicated curation identity — no agent
  alice: {name: Alice Nguyen, teams: [sales], email: alice@acme.com}
  bob:   {name: Bob Rivera, teams: [ops], email: bob@acme.com}
```

Keep the `admin` role on a dedicated identity rather than an employee's account — see [Spaces & Permissions](/concepts/spaces-and-permissions#who-exists-orgyaml).

| Field | Type | Required | Meaning |
|---|---|---|---|
| `people` | map of `id → person` | yes | The key is the person's id (used in vault paths and grants). |
| `name` | string | yes | Display name. |
| `roles` | list of strings | no | Roles this person holds; resolved against `role:` grants. Defaults to none. |
| `teams` | list of strings | no | Teams this person belongs to; resolved against `team:` grants. Defaults to none. |
| `email` | string | no | The person's address, used by [`brain ingest --from`](/guides/getting-things-in#email-in) and [`brain webhook`](/reference/cli#brain-webhook) sender-email routing to resolve intake to them. Must be unique across people; a duplicate is a load error. |

Field **types** are validated: a scalar where a list is expected (`roles: admin` instead of `roles: [admin]`) is rejected rather than silently coerced.

## `spaces.yaml`

```yaml
spaces:
  - {path: Company,     read: [everyone],        write: ["role:admin"]}
  - {path: "Teams/*",   read: ["team:{name}"],   write: ["team:{name}"]}
  - {path: "People/*",  read: ["person:{name}"], write: ["person:{name}"]}
  - {path: "Clients/*", read: ["role:admin"],     write: ["role:admin"]}
```

| Field | Type | Meaning |
|---|---|---|
| `path` | string | The space path. A trailing `/*` makes it a wildcard over one segment. |
| `read` | list of grants | Who may read notes in this space. |
| `write` | list of grants | Who may write them. |

### Grants

| Grant | Matches |
|---|---|
| `everyone` | Every person in `org.yaml`. |
| `role:<name>` | Anyone whose `roles` include `<name>`. |
| `team:<name>` | Anyone whose `teams` include `<name>`. |
| `person:<id>` | Exactly that person. |

### The `{name}` binding

In a wildcard rule, `{name}` binds to the matched path segment. `Teams/*` with `read: ["team:{name}"]` means "the `Teams/sales` space is readable by the `sales` team" — one rule covers every team without enumerating them.

### Exact beats wildcard

When a space matches both an exact rule and a wildcard, the exact rule wins. Define `Teams/*` for the general case and add a specific `Teams/leadership` rule to carve one exception — the wildcard still governs every other team.

<Callout type="warning">
  A path that matches **no** rule resolves to no space. The compiler excludes it
  from every slice and write-back rejects edits to it. Unmatched is closed, not
  open — there is no implicit "readable by default."
</Callout>

## `_meta/config.yaml` — vault-level settings

Optional. Three keys name the vault's top-level trees:

```yaml
# _meta/config.yaml — vault-level naming
entities: Clients   # top-level tree for third-party spaces
entity: client      # singular form: used in guidance text and as the
                    # request frontmatter key (client-name:) and folder
                    # (ClientRequests/)
shared: Company     # the shared top-level space everyone reads
```

Missing file or keys fall back to the defaults shown (a missing `entity`
derives from `entities` by stripping a trailing "s"). A malformed file fails
the cycle loudly rather than silently reverting the vault's vocabulary.
Change the pair on a live vault with [`brain rename-entities`](/reference/cli#brain-rename-entities), not by hand —
the command also renames the folder and rewrites the affected rules and
pending queues.

`entities` may not be `Company`, `Teams`, `People`, or `_meta` (checked case-insensitively), and may not equal `shared`. `shared` may not be `Teams`, `People`, or `_meta`, and is set at `brain init --shared` — it has no rename command, so pick it at the start. When a key is absent the default applies; permissions never depend on any of these names — `spaces.yaml` is the only authority on who reads what.

The default pair (`Clients`/`client` → `ClientRequests/`, `client-name:`) is one case of a general rule: the request folder is `entity` with its first letter capitalized, plus `Requests` (`family` → `FamilyRequests/`), and the frontmatter key is `<entity>-name` (`family-name:`). Reach for `--entity`/`entity:` whenever the naive plural-stripping default would get an irregular noun wrong, e.g. `--entities Families --entity family`.

## Changing the org

Adding a person, a team, or a space is an edit to these two files plus a `brain compile`. There is no migration step: the compiler reads the current `org.yaml` / `spaces.yaml` on every run, so the next compile reflects the change for everyone.

## `webhook.yaml`

Declares the sources [`brain webhook`](/reference/cli#brain-webhook) serves — opt-in to activate, but recommended for any deployment with push sources (meeting recorders, automation platforms). `brain init` scaffolds a commented `_meta/webhook.yaml.example`; copy it to `webhook.yaml` to enable. Each source is one URL path (`/hook/<id>`), one verification mode, and one routing rule:

```yaml
sources:
  - id: fathom-alice                # POST /hook/fathom-alice
    person: alice                   # fixed routing
    verify: standard-webhooks       # HMAC-signed senders (Fathom, Composio, …)
    secret_env: WEBHOOK_FATHOM_ALICE_SECRET
    source: fathom                  # provenance label; defaults to the id
    body_field: transcript          # payload field for the note body (dotted paths ok)
    title_field: title              # payload field for the title (optional)

  - id: zapier-intake
    route: sender-email             # resolve the person from the payload
    email_field: email              # …via this field, against org.yaml emails
    verify: token                   # shared-secret header (Zapier, Make)
    secret_env: WEBHOOK_ZAPIER_TOKEN
```

| Field | Required | Meaning |
|---|---|---|
| `id` | yes | URL path segment; lowercase letters, digits, hyphens. Must be unique. |
| `verify` | yes | `standard-webhooks` (HMAC-SHA256 signatures with replay protection) or `token` (`Authorization: Bearer` / `X-Brain-Token` header). |
| `secret_env` | yes | Name of the **environment variable** holding the secret. The secret itself never lives in this file; an unset variable refuses startup. |
| `person` | one of | Route every delivery to this person's Inbox. |
| `route: sender-email` | one of | Resolve the person from the payload's `email_field` against `org.yaml` emails — unknown senders are refused. Exactly one of `person`/`route` per source. |
| `email_field` | no | Payload field for sender-email routing. Default `email`. |
| `source` | no | Provenance label stamped on each note. Default: the source id. |
| `body_field` / `title_field` | no | Payload fields for the note body and title (dotted paths reach nested JSON). Defaults `body` / `title`. |
| `rate_limit` | no | Max accepted deliveries per minute for this source. Default `60`. Excess deliveries get a retryable `429` with a `Retry-After` header — providers redeliver them, so a backfill slows down rather than dropping notes. Raise it before a bulk import; lower it for a source that should stay quiet. |

Validation fails closed: any invalid entry rejects the whole file, and `brain doctor` reports config errors and unset secret variables.

## `_meta/cache/health.json` — the generated health snapshot

Unlike everything above, this one is **written by brainkit, not by you**. Every
[`brain cycle`](/reference/cli#brain-cycle) overwrites it with what
[`brain doctor`](/reference/cli#brain-doctor) found, reduced to counts:

```json
{
  "schema": 1,
  "generated_at": "2026-08-19T20:30:00Z",
  "brainkit_version": "0.4.3",
  "ok": false,
  "counts": { "error:symlinks": 1, "warn:fact-conflict": 3 },
  "tamper": { "clients": 0, "shares": 0, "promotions": 0 }
}
```

It exists so a control plane can answer "is this brain healthy?" without an
operator opening a terminal — `doctor`'s exit code cannot carry that, because
only `error` severity moves it and most findings are warnings.

**Counts and check ids only — never a finding's message or its paths.** Finding
text quotes note paths and can name a restricted client, so the reduction
happens at the source rather than being filtered downstream by whoever reads
the file.

Three things worth knowing if you consume it:

- **It lives under `_meta/cache/`, which `brain init` gitignores**, so the
  snapshot never enters git, never compiles into anyone's vault, and never
  travels to a clone. A master predating that template gets **no file at all**
  rather than a committable one, and `brain cycle` says so in its
  `health_warnings`.
- **Absence means "cannot say", never "no findings".** A box running a brainkit
  older than 0.4.3 publishes nothing. Reading that as a clean brain is the one
  mistake this file exists to prevent.
- **`ok` is derived** — it is false exactly when some `error:` key is present,
  so it never disagrees with `counts`.

## `.brain/retrieval-stats.json` — the generated retrieval snapshot

Written by every search into each vault's `.brain/` directory. It answers one
question that nothing else in brainkit answers: **is search returning
anything?**

```json
{"schema":1,"person":"joe","brainkit_version":"0.4.5","updated_at":"2026-08-19T14:02:11Z","searches":412,"zero_hit":157,"by_mode":{"hybrid":380,"no-index":2},"warn":{"vector-degraded":8},"raw_log":false,"raw_log_since":null,"raw_truncated":false}
```

Counters are cumulative and only ever increase. They restart at zero if the
vault is rebuilt, which is why the useful reading is the ratio
`zero_hit / searches` rather than either number alone.

`by_mode` keys are the search modes: `hybrid`, `hybrid+graph`, `keyword-only`,
`keyword-only+graph`, and `no-index` for a search that ran before
`brain index` had built anything. `warn` counts categories, never messages —
warning text can contain a filesystem path, and this file never carries one.

The file is compact single-line JSON because it is read by line-oriented
tooling. `jq .` makes it readable.

`.brain/` is gitignored (see the vault `.gitignore` every compile writes), so
this never enters git history or a compiled vault.

### The raw query log

Off by default. Create the sentinel to switch it on for one person:

```bash
touch <vault>/.brain/retrieval-log.on      # on
rm <vault>/.brain/retrieval-log.on         # off
```

While it exists, each search appends a line to `<vault>/.brain/retrieval.jsonl`
holding the query, the mode, and the path and space of each hit. **Note
snippets are never written.** The file is capped at 5 MB; on reaching the cap
it stops appending and sets `raw_truncated` rather than dropping lines
silently.

This log holds the literal text people typed. `raw_log` and `raw_log_since` in
the stats file report that it is running and since when, so it cannot be
switched on and forgotten.

## Embeddings

Retrieval's semantic leg needs an embedding provider. Without one, `brain index` and `brain search` still work in **keyword-only** mode — configure a provider to add the vector leg. Any OpenAI-compatible `/embeddings` endpoint works (OpenAI, Together, a company proxy, a local `llama-server`).

Configure via environment variables:

| Variable | Default | Meaning |
|---|---|---|
| `BRAIN_EMBED_BASE_URL` | — | Endpoint base, e.g. `https://api.openai.com/v1`. **Set this to enable vectors.** |
| `BRAIN_EMBED_API_KEY` | — | Bearer token for the endpoint. |
| `BRAIN_EMBED_MODEL` | `text-embedding-3-small` | Embedding model id. |
| `BRAIN_EMBED_DIM` | `512` | Output dimension (sent as `dimensions`). |
| `BRAIN_EMBED_CACHE` | `~/.cache/brain/embeddings.db` | Embedding cache location. |

Or a config file at `~/.config/brain/config.yaml` (override the path with `BRAIN_CONFIG`):

```yaml
embeddings:
  base_url: https://api.openai.com/v1
  model: text-embedding-3-small
  dim: 512
  api_key_env: OPENAI_API_KEY   # the key is read from this env var, never stored here
```

<Callout type="warning">
  Configuring a provider means each note's text is sent to that endpoint to be
  embedded. On the server, `brain cycle --index` caches embeddings under
  `_meta/cache/` so a chunk shared across people is embedded once. A model
  change forces a full re-embed of every chunk.
</Callout>
